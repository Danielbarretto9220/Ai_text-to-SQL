## SQL generation & validation (§4, §5)

| Module | Location | Status | Notes |
|---|---|---|---|
| LLM client | `app/llm/client.py` | ✅ | Provider history: Google AI Studio/Gemini (`google-genai`) → xAI Grok → Anthropic Claude → **Groq** (2026-08-21), each switch driven by cost/quota reality rather than preference — Gemini's free tier was too rate-limited (~20 requests/day observed), xAI and Anthropic both require paid billing before any call succeeds, and Groq is the one genuinely free (no-card) option tried. `call_llm()`'s shape is unchanged across every switch — takes `prompt_builder.build_prompt()`'s output directly, no DB access, no retrieval re-run. Uses the `openai` SDK pointed at `https://api.groq.com/openai/v1` (Groq documents its API as an OpenAI-compatible drop-in, same pattern as the earlier xAI integration) with `response_format={"type": "json_object"}` (JSON mode — deliberately not Groq's `json_schema` strict mode: live-tested against this project's actual schema first, and Groq's strict-mode validator rejects the model's own **correct** output for nullable/`anyOf` fields, a Groq-side bug not a schema mistake; see the module's own docstring for the repro). Model selection is tiered as a quota lever: `GROQ_MODEL` (`openai/gpt-oss-20b`) handles every first attempt, and `call_llm()`'s one repair retry escalates to `GROQ_ESCALATION_MODEL` (`openai/gpt-oss-120b`). **Live-verified under Groq**: both `test_llm.py` cases pass (correct SQL generation, correct use of the `insufficient_context` escape hatch); 6/7 `test_pipeline.py` cases pass, the one failure being a genuine SQL-quality miss (a nonexistent column alias) by the smaller free model, not a plumbing bug. Does **not** do SQL validation, guardrails, cost estimation, or orchestration — those stay separate items below (§6.5, §8) |
| Structured-output schemas | `app/llm/schemas.py` | ✅ | One `SQLGenerationResponse` Pydantic model covers both branches of the seeded system prompt's contract (normal SQL response and the `{"error": "insufficient_context", ...}` shape). Originally shaped around Gemini's `response_schema` locking the model to exactly one schema; unchanged across every later provider switch since every field was already optional and `is_error_response()` already did the branching — each weaker JSON-mode guarantee (xAI, then Groq) just makes that existing design earn its keep more (§3.4) |
| SQL parser / hallucination check | `app/validation/sql_parser.py` | ✅ | `sqlglot` only (`dialect="postgres"`) — not `pglast`: `pglast` binds to the real PG C parser and needs native compilation, and this repo already has a documented, painful Windows build history with `pgvector`. `parse_sql()` (syntax), `is_read_only()` (root node must be `exp.Select` — defense in depth, never trusts the LLM followed the system prompt's own read-only rule), `check_hallucinations()` (resolves aliased/unqualified column refs against `meta.tables`/`meta.columns`), `check_joins()` (every JOIN...ON validated against `app/retrieval/relationship_graph.build_graph()`, reused not requeried) (§5) |
| Guardrails (read-only, LIMIT, complexity, business rules) | `app/validation/guardrails.py` | ✅ | `enforce_limit()` injects `LIMIT 100` unless the query is a pure aggregate (system prompt rule 4); `check_complexity()` caps joins/subqueries; `check_business_rules()` dispatches each active `meta.business_rules` row to a per-`rule_type` checker (5 distinct `rule_logic` shapes, and even inconsistent key names within `forbidden_aggregation` — dispatch is defensive, try/except per rule, unknown `rule_type` skipped). **Bug found and fixed during testing**: the first implementation only resolved qualified column references (`alias.column`), silently missing violations on unqualified single-table queries — which is how the LLM writes SQL most of the time. Fixed by resolving the empty-string qualifier to the query's sole table when unambiguous; re-verified all 8 seeded rules correctly trigger afterward (§5) |
| Cost estimator (`EXPLAIN` check) | `app/validation/cost_estimator.py` | ✅ | `EXPLAIN (FORMAT JSON)` — always safe/read-only regardless of whether the query is ever actually executed. Threshold constants are generous defaults sized for this project's tiny dataset, not tuned against real volume (§5) |
| Full pipeline orchestration (retrieval → prompt → LLM → validate → execute) | `app/pipeline.py` | ✅ | `validate_sql()` combines all three validation modules into one pass/fail report. `generate_validated_sql()` is the end-to-end entry point (`build_prompt()` → `call_llm()` → `validate_sql()` → **one** repair attempt on validation failure, re-calling the LLM with the validation errors appended — a separate retry loop from `app/llm/client.py`'s own JSON-shape repair retry, per the doc's exact "one automatic repair attempt" wording). Live-verified: a real question passes validation clean on the first attempt; an artificially-forced first-attempt failure correctly triggers the repair retry and the LLM self-corrects. `execute_query()` is opt-in only (never auto-invoked) — `SET TRANSACTION READ ONLY` + `statement_timeout` + row cap, always rolled back, never committed. Live-verified as genuine defense in depth: calling it directly with an `UPDATE` (bypassing all validation) is rejected by Postgres itself (`ReadOnlySqlTransaction cannot execute UPDATE in a read-only transaction`), not just by the Python-level guardrails (§4) |

## Running the moved modules

`pip install -r requirements.txt` installs the pinned dependencies (added alongside the LLM client module —
previously only tracked in README prose). There's still no `pyproject.toml`/packaging, so run modules from
the repo root using `-m` so `app`/`workers` resolve as packages, e.g.:

```
python -m app.db.metadata_loader
python -m app.db.models
python -m workers.reindex_embeddings
python -m workers.generate_docs
python -m workers.drift_detector
python -m workers.sync_data_content
python -m workers.scheduler
python -m app.retrieval.vector_search
python -m app.retrieval.relationship_graph
python -m app.retrieval.hybrid_search
python -m app.retrieval.rerank
python -m app.retrieval.confidence
python -m app.prompting.prompt_builder
python -m app.llm.client
python -m app.validation.sql_parser
python -m app.validation.guardrails
python -m app.validation.cost_estimator
python -m app.pipeline  # full end-to-end pipeline demo
```
